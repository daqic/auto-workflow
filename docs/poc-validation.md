# auto-workflow POC 建设与验证记录

本文只记录 `auto-workflow` 仓库的具体工具映射、建设状态和验证边界。跨项目、跨框架的规则以[前端 AI 自动化工作流手册](ai-frontend-workflow.md)为准。

## 1. 本仓库的工具映射

| 工作流能力    | 本仓库实现                                      |
| ------------- | ----------------------------------------------- |
| 包管理器      | pnpm，版本由 `package.json#packageManager` 固定 |
| 运行时        | Node.js，版本由 `package.json#engines` 固定     |
| 类型检查      | vue-tsc                                         |
| 代码问题检查  | ESLint                                          |
| 格式          | Prettier                                        |
| 单元/组件测试 | Vitest                                          |
| 浏览器测试    | Playwright                                      |
| 任务追踪      | 当前 GitHub remote 对应仓库的 Issues            |
| 远程门禁      | GitHub Actions                                  |
| 设计事实源    | 需求中记录的最终批准 Penpot 版本                |
| 最终合并权限  | 人工审核并手工合并                              |

固定命令：

```bash
pnpm install --frozen-lockfile
pnpm run dev
pnpm run fix
pnpm run check
pnpm run check:all
```

## 3. 新试用需求的输入契约

开始实现前，规格 Issue 至少应明确：

- 原始输入、目标用户和需要解决的问题。
- 已确认范围、明确的范围外内容和可观察的验收标准。
- 依赖、风险、验证方法和仍需人工决定的问题。
- UI 适用时的 Penpot 文件、Page、Frame/Board/Node、批准版本或读取时间。
- 需要覆盖的主路径、关键状态、视口、文案、资源和无障碍要求。
- 人工批准记录，以及是否满足 `ready-for-agent` 条件。

本地代码原型不是默认 UI 输入。如果确实需要用一次性原型回答独立设计问题，应将问题和结论记录到 Issue 或 ADR；原型代码不得长期留在主分支，也不能替代批准的 Penpot 设计。

## 4. 工作流验证清单

| 验证点   | 必须验证的内容                                                       |
| -------- | -------------------------------------------------------------------- |
| Issue    | 聊天不是唯一来源；需求、来源、范围、验收和批准记录可以追溯           |
| Penpot   | 读取正确文件和页面；实现依据指向准确对象和批准版本；凭据未进入仓库   |
| DoR      | 高影响问题已解决，设计和依赖完整，并有明确人工批准                   |
| 实现     | 只完成当前 Issue 的最小完整改动，没有无关 diff 或工具绕过            |
| 本地门禁 | 通过最接近行为的测试、`pnpm run check` 和适用的 `pnpm run check:all` |
| 远程 CI  | 冻结 lockfile 安装并验证最终 head SHA；失败会阻塞后续步骤            |
| 代码审查 | 同时检查工程规范和规格符合度，阻塞问题修复后针对新 SHA 重新检查      |
| 人工合并 | 人核对需求意图、最终 UI、风险和回滚，并保持最终合并权限              |
| 上线反馈 | 部署、冒烟、监控、回滚或重开 Issue 保留与需求、PR 和 commit 的关联   |

## 5. 当前后续工作

1. 在新的 GitHub 仓库初始化分诊标签和分支保护。
2. 在真实 PR 上重新验证 `ci` 与 `e2e`，确认失败和恢复都作用于最终 head SHA。
3. 提交第一条新试用需求，并完成需求澄清与人工批准。
4. 读取该需求指定的 Penpot 设计，补齐设计来源和验收视口。
5. 跑通实现、浏览器验收、远程 CI、独立审查和人工合并闭环。

当前不建设自动合并。所有机器检查通过后，仍由人完成最终审核和手工合并。
